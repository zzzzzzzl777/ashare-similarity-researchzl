# 数据边界说明

## 本地会落盘什么

默认数据目录在：

- 源码仓库模式：`data/`
- 安装模式：`~/.ashare_similarity/data`

主要内容包括：

- `raw/`: 原始行情 parquet
- `cache/`: 股票池、资料、市场/行业上下文缓存
- `index/`: 特征矩阵、元数据、ANN 索引工件
- `reports/`: 导出结果
- `workspace.duckdb`: 回填状态、失败样本、构建记录
- `run_logs/`: 本地运行状态和辅助日志

这些文件都属于本地运行工件，不是源码仓库资产。

## 哪些东西不要提交到 GitHub

- `data/` 下的真实缓存和索引
- `*.duckdb`
- `run_logs/`
- 导出的 CSV / HTML 报告
- 大体积样本数据、临时调试文件、日志
- 任何包含局域网 IP、代理信息、VPN 配置或内部路径的敏感环境信息

仓库当前的 `.gitignore` 已经覆盖常见本地工件，但提 PR 前仍应人工确认一次。

## 大文件与存储增长边界

这不是小概率问题，而是正常运行结果：

- 原始行情数据会随着回填范围扩大而增长
- 索引目录会随着窗口和频段增加而增长
- 导出报告、调试产物和临时日志也会积累

所以当前 GitHub 交付边界应理解为：

- GitHub 负责代码、文档、测试、模板和工作流
- 本地磁盘负责缓存、索引、元数据和导出结果

如果需要分享问题现场，不要上传整个 `data/` 或 `workspace.duckdb`；优先分享文本化诊断结果。

## 免费数据源边界

免费数据源的限制属于项目真实能力边界：

- 外部网络只用于拉取公开行情数据
- 上游失败、限流、超时、代理抖动属于数据源可用性问题
- 日线是“逐步回填后尽可能全”，不是首次启动即全市场就绪
- 分钟线是“近期窗口可用”，不是全历史分钟数据库
- `1` 分钟数据通常只能稳定覆盖最近 `5` 个交易日
- 免费源之间的复权口径、成交量和补齐速度可能存在差异

这不等于项目缺少“注册安全 / 邮件系统 / 风控系统”；那是另一类并不适用于当前仓库的问题。

## Issue / PR 中应该提供什么

如果要报告 bug，优先提供：

```bash
python -m ashare_similarity.cli doctor
python -m ashare_similarity.cli status --frequency daily
```

如果问题与分钟线或特定维护命令有关，再补充：

- 出问题的频段
- 窗口大小
- 股票代码
- 截止日期
- 触发问题的命令或 API 路径
- 相关 traceback 或报错全文

如果 `doctor` / `status` 自身就失败，也请直接贴失败输出；这仍然是有价值的诊断信息。

## Issue / PR 中不应该出现什么

- 整个本地缓存数据目录
- 整个 DuckDB 文件
- 全量索引目录压缩包
- 未打码的本机绝对路径、用户名目录
- 内网地址、代理口令、VPN 信息
- 与问题无关的大体积导出文件

## 可以安全分享的材料

- `doctor` 的文本输出
- `status` 的文本输出
- 复现步骤
- 最小 traceback
- 少量、脱敏后的截图
- 少量、脱敏后的样例记录

注意：`doctor` 输出会包含本地数据根目录、DuckDB 路径等信息。对外公开前，请按需要打码用户名目录、机器名或其他敏感路径段。

## 对外贡献者的建议

提 issue 或 PR 前，先自查这几个问题：

- 这是当前本地工具的真实问题，还是未来 SaaS 才会遇到的问题？
- 这是仓库缺陷，还是免费数据边界 / 网络环境造成的限制？
- 你的描述里是否已经包含足够的 `doctor` / `status` / 复现信息？
- 你是否不小心把本地缓存、数据库或导出文件带进提交了？

只要把这些边界讲清楚，社区协作会顺畅很多。
