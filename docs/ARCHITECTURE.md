# 架构说明

## 项目定位

这是一个本地离线优先的 A 股 K 线相似检索系统，目标是：

- 在本机缓存免费行情数据
- 离线构建滚动窗口特征和检索索引
- 通过本地 Web 和 CLI 做秒级相似 K 线查询

它当前不是一个公开注册、多人协作、对外 SaaS 化运营的平台。

如果把“截图里的通用工程担忧”都堆进来，很容易失焦；本文件的目标就是明确哪些问题现在真的适用，哪些暂时不适用。

## 当前架构

### 1. 前台查询

- `FastAPI + Jinja2 + ECharts`
- Web 负责查询、状态查看、导出和页面展示
- 默认查询依赖本地已经存在的缓存和索引
- 默认启动优先绑定 `127.0.0.1`，避免把本地工具误当成局域网公共服务

### 2. 后台维护

- `bootstrap`: 初始化股票池和基础市场环境
- `backfill` / `backfill-loop`: 回填免费行情缓存
- `maintain`: 回填并按需重建默认索引
- `doctor`: 自检当前是否达到“可直接查询”的状态

### 3. 数据分层

- `data/raw`: 原始行情 parquet
- `data/cache`: 股票池、行业/市场上下文、资料缓存
- `data/index`: 不同窗口长度的特征、清单和 ANN 索引
- `workspace.duckdb`: 回填状态、失败样本、构建记录等元数据

## 真实的并发与异步模型

这里最容易被误判。

- Web 路由是 `async`，所以 HTTP 层支持异步处理。
- 但核心维护逻辑不是独立的异步任务系统，也不是消息队列 worker。
- `backfill`、`backfill-loop`、`maintain`、`build` 都是显式由 CLI 触发的同步流程。
- 查询和维护在职责上是解耦的，但不是“天然无冲突”；同一份本地存储仍可能产生文件占用和资源竞争。

对当前项目真正相关的问题是：

- 不要把重建索引或大规模回填塞进 Web 查询请求
- 不要假设当前有分布式任务队列、任务抢占或多 worker 协调
- 在同一工作目录下，重维护操作应由单个操作者顺序执行

因此推荐操作是：

- 先停 Web，再执行 `maintain` 或批量 `build`
- 维护完成后，再重新启动 Web

## 存储结构与大文件问题

存储不是附属细节，而是核心设计。

- Parquet 负责落原始时序数据和部分上下文数据
- DuckDB 负责记录缓存注册表、构建记录、回填 run、失败样本
- 索引目录会额外保存 `matrix.npy`、`metadata.parquet`、`manifest.json`、可选 `ann_index.faiss`

这意味着下面这些担忧是适用的：

- 原始数据和索引文件会随着标的数量、频段和窗口规模持续增长
- 本地导出和临时运行状态不适合进 Git
- DuckDB 虽然轻量，但仍然是单机文件型存储，不适合被误解成“多人共享中心库”

当前仓库的 Git 边界是：

- 应提交代码、文档、测试、模板、CI 配置
- 不应提交 `data/`、`*.duckdb`、`run_logs/`、导出文件和日志

## 免费数据与回填架构

免费数据边界会直接影响架构理解。

- 日线目标是逐步回填后做到“尽可能全”的本地缓存
- 分钟线目标是近期历史窗口检索，不是全历史分钟数据库
- 数据源本身可能限流、超时、断连或口径不完全一致

当前工程上已经有的应对方式：

- 单只股票失败不会拖垮整个批次
- 失败样本会持久化到 DuckDB，便于后续重试
- `backfill-loop` 能沿用同一个未完成 run 持续推进
- `doctor` 和 `/api/status` 会暴露缓存覆盖、索引缺口和最近失败样本

因此，“免费源不稳定”是当前项目的核心现实约束；这比“账号风控”之类并不存在的系统更值得优先讨论。

## 性能与 GPU 现状

GPU 是相关话题，但当前状态需要说实话。

- 可选 ANN 路径存在：FAISS、`sklearn`、NumPy
- `faiss` 是可选依赖；仓库 extras 当前提供的是 `faiss-cpu`
- 如果没有 `faiss`，会退回 `sklearn` 或 NumPy 的 CPU 路径
- `doctor` 会检测当前索引后端、`faiss` 可用性、FAISS GPU API 能力和 `torch.cuda` 状态

但当前没有做到的事情也要明确：

- 仓库没有默认接通完整 GPU 检索后端
- 仓库没有自动把现有索引迁移到 GPU
- AKShare 回填、DuckDB 写入和大部分 Pandas/Polars 整理也不是主要 GPU 受益点

更准确的说法是：

- “GPU 对未来检索加速可能有帮助”是相关判断
- “当前项目已经是成熟 GPU 检索系统”是不准确的判断

## 这些担忧当前适用

- 并发与前后台解耦
- 同一本地存储上的文件争用
- 存储分层与数据落盘策略
- 大文件增长和 Git 提交边界
- 免费数据覆盖范围、可靠性和回填恢复
- CPU / FAISS / GPU 加速路径的真实状态

## 这些担忧当前不适用

- 用户注册与登录系统
- 邮件验证码、自建邮件投递链路
- 批量注册、IP 池、验证码绕过
- UGC 发帖评论、安全审核、内容风控
- 多租户数据隔离和公网 SaaS 控制面
- 计费、订阅、公开 API 配额体系

原因很简单：当前项目是本地单机工具，没有用户体系，也没有公网暴露的多用户入口。

## 如果以后做成 SaaS，再补什么

- 用户体系、鉴权、限流、验证码、审计日志
- 多进程 / 分布式任务队列
- 独立对象存储和任务编排
- 公网访问面的安全加固
- 多租户数据隔离
- 观测、告警、成本与配额治理

这些不是“不重要”，而是“当前阶段不应假装已经需要完整解决”。
